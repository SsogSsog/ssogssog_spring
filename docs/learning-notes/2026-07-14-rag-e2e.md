## 2. Spring AI 문법과 실제 역할

### 검색 요청

```java
SearchRequest.builder()
        .query(question)
        .topK(4)
        .build();
```

- `query`: 의미 검색에 사용할 원문 질문
- `topK`: 가장 가까운 문서 몇 건을 가져올지 지정
- `filterExpression` 없음: Day3의 접수번호 정확 매칭과 달리 질문 의미가 검색 기준

```java
vectorStore.similaritySearch(searchRequest);
```

이 한 줄 내부에서 `EmbeddingModel`이 질문을 임베딩하고 pgvector가 유사도를 계산한다. 서비스가 `embed()`를 직접 호출하지 않는다.

### user 프롬프트 변수 주입

```java
.user(user -> user
        .text(userPrompt)
        .param("context", context)
        .param("question", question))
```

- `.text(userPrompt)`: `disclosure-rag-user.st`를 사용자 메시지의 틀로 사용
- `.param("context", ...)`: 템플릿의 `{context}` 치환
- `.param("question", ...)`: 템플릿의 `{question}` 치환
- 실제 질문은 파일에 저장하는 것이 아니라 HTTP 요청으로 받아 실행 시 주입한다.

### 답변과 토큰 계측

```java
ChatResponse response = ...call().chatResponse();
String answer = response.getResult().getOutput().getText();
tokenMetrics.record("rag-ask", response);
```

`ChatResponse`를 받는 이유는 답변 문자열뿐 아니라 토큰 사용량도 함께 계측하기 위해서다.

## 3. 확인된 한계와 트러블슈팅

### 기업명 질문에 보수적으로 답한 이유

`삼성전자 자기주식 처분 관련 공시가 있어?`로 질문했을 때 검색 자체는 성공했지만, 모델은 삼성전자 공시인지 단정하지 않았다.

- 현재 `Document.text`: 공시 제목
- 현재 metadata: `receiptNo`, `reportName`, `submitter`, `date`
- 없는 정보: `corpCode`, `companyName`

모든 20건이 삼성전자 조회 결과라는 사실을 LLM에게 전달하지 않았으므로, 모델의 보수적인 답변이 정상이다.

향후 과제: 적재 metadata에 기업 식별 정보를 추가하고 프롬프트 context 또는 검색 필터에 반영한다.

### 하나의 vector_store에 다른 실험 문서가 섞임

기업명이 포함된 질문에서는 과거 임베딩 실험 문서가 top 4에 함께 검색됐다. 현재 검색은 vector_store 전체를 대상으로 하기 때문이다.

향후 과제: `documentType=disclosure` 같은 metadata를 적재하고 Day5에서 공시 문서만 필터링한다. 이번 Day4에서는 metadata 필터·검색 품질 튜닝을 진행하지 않는다.

### PostgreSQL metadata 타입

건수 확인 중 아래 SQL은 실패했다.

```sql
metadata ? 'receiptNo'
```

현재 컬럼이 `json` 타입이므로 jsonb 연산자 `?`를 사용하려면 캐스팅이 필요했다.

```sql
metadata::jsonb ? 'receiptNo'
```

캐스팅 후 공시 벡터 **20건**을 확인했다.

# Day5 — 검색 품질: 출처 표시 + threshold (2026-07-15)

## 1. 출처 표시 (Day4 한계 해소)

Day4에서 `buildContext`가 `Document.getText()`(제목)만 프롬프트에 실어, 답변에 회사·날짜를 못 붙이는 한계가 있었다. `getMetadata()`의 `submitter`·`date`를 함께 조립하도록 고쳤다.

- 출력 형식: `1. [삼성전자 · 20260710] 자기주식처분결과보고서`
- metadata가 없으면 `metadataOrDefault`로 "회사 미상"·"날짜 미상" 대체 → LLM이 출처를 지어내지 않도록 시스템 프롬프트에도 "미상은 밝히지 마라" 명시.
- **깨달음**: 벡터 DB의 **metadata 설계가 곧 나중에 필터링·출처 표시로 할 수 있는 것의 상한**. text(의미검색 대상)와 metadata(정확매칭·출처)를 무엇으로 나눠 넣느냐가 핵심.
- **실측 함정**: `submitter`가 회사명이 아니라 **제출인 개인명**인 공시가 많다(얀손헨릭·전중원·Lee Sungki…). 자기주식/실적 등 회사 자체 공시만 "삼성전자". 즉 지금 출처는 "제출인" 표기이고, 정식 회사명/종목코드는 별도 metadata 필드가 필요 → 향후 과제.

## 2. threshold (무관 질문 차단)

`SearchRequest.builder().similarityThreshold(0.7)` 추가. `topK(4)`와 AND로 걸린다: 0.7 미만은 버리고 남은 것 중 최대 4개.

- Day4 자기주식 검색의 4번째(0.6970)가 0.7 미만이라 잘려 **4건→3건**.
- 무관/미보유 질문은 검색 **0건** → `buildContext`가 "검색된 공시가 없습니다" → 시스템 프롬프트 "근거 없으면 모른다" 발동 → 환각 차단.
- **트레이드오프**: 높이면 정밀도↑재현율↓(유용한 약한관련 놓침), 낮추면 반대. 0.7은 실측 분포(관련 0.76~0.82, 무관≈0.53) 기반 시작값. 평가셋 기반 튜닝은 향후 과제.

## 3. 질문 10개 눈 검수 (실측)

**전제 정리**: pgvector에 Day1~2 학습용 테스트 문서(김치찌개 등, submitter 없는 12건)가 섞여 "점심 뭐먹지"가 0.76으로 통과하는 오염 발생 → submitter 없는 12건 삭제, 실제 공시 20건만 남기고 재검수.

| 질문 | 검색 | 점수 | 답변 |
|---|---|---|---|
| 자기주식 처분 공시? | 3건 | 0.81/0.79/0.79 | 출처 3건 정확 제시 |
| 잠정 실적 발표? | 1건 | 0.77 | 출처 붙여 정답 |
| IR 개최 공시? | 1건 | 0.82 | 정답 |
| 장래 경영계획? | 2건 | 0.80/0.78 | 원본+기재정정 2건 |
| 임원 주식 소유? | 4건 | 0.81 | 제출인별 출처 제시 |
| 삼성물산 대량보유? | 1건 | 0.76 | 정답 |
| 배당 결정? | **0건** | — | "확인 어렵다"(실제 없음) |
| 유상증자 공시? | **0건** | — | "확인할 수 없다"(실제 없음) |
| 오늘 날씨? | **0건** | — | "날씨는 제공 불가" |
| 파이썬 크롤링? | **0건** | — | "확인 어렵다" |

**결론**: 관련 6개 모두 적중+출처 정확, 무관/미보유 4개 모두 threshold가 0건 처리해 환각 없음. threshold+출처 표시가 의도대로 동작 확인.

## 4. 배운 것

- **오염 데이터가 threshold를 무력화한다** — 학습용 잡담 문서가 남아있으면 "점심 뭐먹지"도 0.76으로 통과. 컬렉션 위생(무엇을 적재하는가)이 threshold만큼 중요.
- `metadata` 컬럼이 `json` 타입이라 jsonb 연산자(`?`, `jsonb_object_keys`)는 `::jsonb` 캐스팅 필요.
- 출처를 코드가 "미상"으로 뱉으면 프롬프트도 "미상 지어내지 마라"를 알아야 정합 — **코드 데이터 형식 ↔ 프롬프트 설명은 짝을 맞춰야 한다.**
